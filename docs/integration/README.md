# Running Knowledge Acquisition as a service

KA is an independent service. AgentX orchestrates it, Knowledge Worker receives its governed graph changes, and the Data Platform keeps
its bytes. Each peer is reached over HTTP and each is optional. This guide covers deployment, settings, the API, examples and failure
handling. Related documents:

- [`source-inventory.md`](source-inventory.md): what is in the repository, and who owns what.
- [`openapi-v1.json`](openapi-v1.json): the service API, generated by `tools/export_openapi.py`.
- [`../contracts/knowledge-worker-v1-ka.md`](../contracts/knowledge-worker-v1-ka.md) and
  [`../contracts/data-platform-v1-real.md`](../contracts/data-platform-v1-real.md): the two outbound contracts.
- [`../architecture/knowledge-acquisition.md`](../architecture/knowledge-acquisition.md) §13: the design.

## Start it

```bash
uv venv .venv && uv pip install -e ".[dev]"     # once
cp .env.example .env                              # then edit; never commit .env
.venv/bin/python -m ka serve                      # http://127.0.0.1:8011/api/knowledge-acquisition
.venv/bin/python -m ka env                        # every declared setting and whether it is set
```

KA needs no Enterprise OS checkout. With nothing configured it runs on local storage, the in-memory graph shadow and the stub LLM.
`GET /api/knowledge-acquisition/healthz` reports `{status: ok|degraded|down, service_id, version, checks}`. `checks.graph` names where
graph changes go, and `checks.grammar` says whether the grammar loaded. A missing grammar gives `degraded`, not `down`.

## Settings for the service role

| setting | default | meaning |
|---|---|---|
| `KA_SERVICE_ID` | `knowledge-acquisition` | the id KA reports to AgentX |
| `KA_AGENTX_TOKEN` | — | bearer token AgentX presents on `/v1` (AgentX: `AGENTX_KNOWLEDGE_ACQUISITION_TOKEN`). Unset → the console's access policy applies |
| `KA_AGENTX_URL` | — | set → KA pushes its capability list to AgentX on start and on `POST /v1/capabilities/register`; unset → AgentX pulls |
| `KA_GRAPH_MODE` | `auto` | `memory` · `kw` · `eos-local` (deprecated). `auto` → `kw` if `KA_KW_URL`, else `eos-local` if `KA_ENTERPRISE_OS_ROOT`, else `memory` |
| `KA_KW_URL`, `KA_KW_TOKEN` | — | Knowledge Worker base URL and KA's token (scopes `graph-changes:propose`, `graphs:read`) |
| `KA_KW_PUBLISH_WAIT_S` | 30 | how long a console apply waits for KW; AgentX publication waits as long as its operation lives |
| `KA_GRAMMAR_URL` | — | KW's `GET /v1/graph-model`; overrides `KA_GRAMMAR_DIR` |
| `KA_STORAGE_BACKEND` | `local` | `data_platform` puts bytes on the Data Platform |
| `KA_DP_BASE_URL`, `KA_DP_API` | —, `v1` | the Data Platform and which API (`v1` real; `ka-subset` superseded) |
| `KA_DP_AUTH_MODE`, `KA_DP_SERVICE_TOKEN`, `KA_DP_PRINCIPAL`, `KA_TENANT_ID` | `auto`, —, `ka`, `default` | Bearer, or loopback principal headers |

## What AgentX calls

Base: `http://<host>:8011/api/knowledge-acquisition`. All paths below sit under it and need `Authorization: Bearer $KA_AGENTX_TOKEN`.

| call | purpose |
|---|---|
| `GET /v1/capabilities` | seven descriptors: `knowledge.acquire` (async), `.search`, `.read`, `.revise`, `.review`, `.resolve_conflict`, `.publish` (`requires_approval`) |
| `POST /v1/capabilities/{id}/invoke` | an `InvokeRequest` → an `OperationState` (200 sync, 202 async); `Idempotency-Key` honoured |
| `GET /v1/operations/{id}` · `POST …/cancel` | poll or cancel |
| `POST /v1/operations/{id}/input` | answer an `awaiting_input` interaction: `{interaction_id, values, submitted_by}`. The person in `submitted_by` is who decides |
| `GET /v1/tasks` | open review work as tasks |
| `GET /v1/events?after=<seq>` | the note's events (`knowledge.review.required`, `…revision.proposed`, `…conflict.detected`, `…publication.approved`, `…publication.completed`, `…acquisition.completed`), schema `ka.v1` |
| `/v1/acquisitions`, `/v1/knowledge/…`, `/v1/publications` | the requirements note's paths, as aliases of the same capabilities |

### Example: acquire, review, publish

```bash
KA=http://127.0.0.1:8011/api/knowledge-acquisition; H="Authorization: Bearer $KA_AGENTX_TOKEN"
CALLER='{"service_id":"agentx","user":"alice","permissions":["knowledge.acquire","knowledge.review","knowledge.publish"]}'

# 1. acquire: 202 and an operation id at once
curl -s -H "$H" -H 'Content-Type: application/json' -X POST $KA/v1/capabilities/knowledge.acquire/invoke \
  -d "{\"schema_version\":\"1\",\"caller\":$CALLER,\"input\":{\"kind\":\"text\",\"name\":\"Refund SOP\",
       \"raw_content\":\"Refunds above \$500 require manager approval.\",\"scope\":{\"scope_type\":\"DOMAIN\",\"scope_id\":\"merchant-acquiring\"}}}"
curl -s -H "$H" $KA/v1/operations/AXO-…            # → succeeded, result.candidates = ["KN-001:v1"]

# 2. review: awaiting_input with a UiSchema; a named person answers
curl -s -H "$H" -H 'Content-Type: application/json' -X POST $KA/v1/capabilities/knowledge.review/invoke \
  -d "{\"schema_version\":\"1\",\"caller\":$CALLER,\"input\":{\"item_id\":\"KN-001:v1\"}}"
curl -s -H "$H" -H 'Content-Type: application/json' -X POST $KA/v1/operations/AXO-…/input \
  -d '{"interaction_id":"…","values":{"outcome":"APPROVE","reason":"matches the SOP"},"submitted_by":"alice"}'

# 3. publish: running until Knowledge Worker applies the change, then succeeded
curl -s -H "$H" -H 'Content-Type: application/json' -X POST $KA/v1/capabilities/knowledge.publish/invoke \
  -d "{\"schema_version\":\"1\",\"caller\":$CALLER,\"input\":{\"item_id\":\"KN-001:v1\"}}"
```

## Failure handling

| situation | what KA does | what the caller sees |
|---|---|---|
| bad token on `/v1` | refuses | 401 `{"error":{"code":"unauthorized",…}}` |
| caller lacks a capability's permission | refuses before recording anything | 403 `forbidden` |
| input fails the capability schema | refuses before recording anything | 400 `schema_invalid` |
| same `Idempotency-Key`, same body | returns the first operation | the same `operation_id` |
| same key, different body | refuses | 409 `conflict` |
| an agent id, or no user, answers a review | refuses (agents cannot decide) | 403 `forbidden`; the interaction stays open |
| a decision is made in KA's console instead | the waiting operation completes on its next poll | `succeeded` with the console's decision |
| Knowledge Worker holds a change for its own approval | the publish operation stays `running` ("awaiting Knowledge Worker") | `running`, then `succeeded` |
| Knowledge Worker refuses (`STALE_BASE`, `FORBIDDEN`, …) | KA's proposal stays APPROVED for a person to retry | `failed`, `error.details.kw_code` |
| Knowledge Worker unreachable | retryable failure | `failed` `unavailable`, `retryable: true` |
| grammar URL unreachable | grammar not loaded; bindings unresolved | `/healthz` `degraded` |
| Data Platform 5xx / timeout | bytes spooled, upload retried by the outbox | version `pending`, then `available` |
| Data Platform 409/422 | not retried | version `failed` with the DP code |
| AgentX down (push or callback) | retried by the outbox with backoff | nothing lost; AgentX can also pull or poll |

## Two-process check

`e2e/plan33_two_process_flow.py` starts KA (no Enterprise OS root) with a fake AgentX and a fake Knowledge Worker, both over HTTP. It runs
registration, acquisition, review by a named person, publication through Knowledge Worker and the event feed.
`e2e/plan32_dp_real_flow.py` does the same for the real Data Platform.
